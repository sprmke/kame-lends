# Query-native stacks fit tRPC best

The stack that **best suits tRPC** is a Query-native TypeScript React app: **TanStack Start hosting tRPC v11 over the Fetch adapter, `@trpc/tanstack-react-query` plus TanStack Query v5, Zod, Drizzle, Better Auth cookie sessions, React 19 with Tailwind v4 and shadcn, Vitest `createCaller` tests, and a Turborepo `packages/api` that exports `AppRouter` as a type**. That combination keeps tRPC doing the job it was built for (end-to-end inference into a React Query cache, batching, mutations, optional SSE) without splitting data fetching across RSC callers and client hooks ([tRPC homepage](https://trpc.io); [TanStack React Query setup](https://trpc.io/docs/client/tanstack-react-query/setup); [create-t3-turbo](https://github.com/t3-oss/create-t3-turbo)). Next.js App Router remains the **documented and T3 default** for new Next projects, and it is still the **production-default path** because the docs, Vercel cookie story, hiring pool, and Cal.com-scale proof all live there ([Next.js Integration](https://trpc.io/docs/client/nextjs); [Cal.com architecture](https://calcom-cal-com.mintlify.app/developers/contributing/architecture)). Vite plus Fastify or Hono is the cleaner host once the router is a real multi-client API (web, Expo, webhooks, WebSockets), not a page-data layer ([Adapters overview](https://trpc.io/docs/server/adapters); [Fastify adapter](https://trpc.io/docs/server/adapters/fastify)). Those three hosts are not competing “best stacks.” They are the same tRPC core on different runtimes. tRPC itself is the wrong premise when the consumer cannot import `AppRouter`: public OpenAPI products, Swift/Kotlin partners, contract-first split teams, and idiomatic SvelteKit or Remix apps that already have typed loaders.

## tRPC still wants a Query cache, not a Server Component

tRPC’s contract is a TypeScript router whose **type** is the SDK. The client is `createTRPCClient<AppRouter>`, procedures infer from validators, and the recommended React path in 2026 is **`@trpc/tanstack-react-query` with Query v5**, not the classic `trpc.x.useQuery()` proxies ([Vanilla client](https://trpc.io/docs/client/vanilla); [TanStack React Query setup](https://trpc.io/docs/client/tanstack-react-query/setup)). Current published server is **`@trpc/server` 11.19.0**, requiring TypeScript **≥ 5.7.2**, React ≥ 18.2, Node 18+, and Fetch `Request`/`Response` on the wire ([npm `@trpc/server`](https://registry.npmjs.org/@trpc/server/latest); [Migrate from v10 to v11](https://trpc.io/docs/migrate-from-v10-to-v11)). That design peaked on the Pages Router, where `@trpc/next` wrapped providers, SSR, and `createNextApiHandler` into one product ([Next.js Integration](https://trpc.io/docs/client/nextjs)). App Router is now “the recommended approach for new Next.js projects,” but the HTTP layer is the **Fetch adapter** in `app/api/trpc/[trpc]/route.ts`, providers are manual, and RSC already “solves a lot of the same problems tRPC was designed to solve” ([App Router setup](https://trpc.io/docs/client/nextjs/app-router-setup); [RSC + TanStack Query](https://trpc.io/docs/client/tanstack-react-query/server-components)). A `createCaller` invocation inside a Server Component **does not** land in the Query cache. Prefetch through `createTRPCOptionsProxy` plus `HydrationBoundary` does. That split is the App Router tax: two clients, a per-request QueryClient, streaming `pending` dehydrations, and a standing temptation to drop tRPC for RSC plus Server Actions.

TanStack Start is the closer conceptual host because it keeps **TanStack Query as the canonical cache**. Official example work uses `fetchRequestHandler` on a catch-all, an isomorphic client (in-process link on the server, HTTP batch plus subscriptions in the browser), and QueryClient wiring in the router ([trpc/trpc PR #7024](https://github.com/trpc/trpc/pull/7024)). Tanner Linsley has said Start will **not** turn server functions into a tRPC clone; teams that need a public HTTP API should use **tRPC or Hono**, not `createServerFn` ([TanStack/router #3884](https://github.com/TanStack/router/discussions/3884)). T3 Chat left Next for Start in January 2026, **kept tRPC**, and stayed on Vercel; the Next router had been hacked around (`ssr: false`, custom headers so SPA fallbacks would not swallow `/api/trpc`) because “if the Next.js router is not the right router for your app, then Next.js is not the right framework” ([Rosetta transcript](https://rosetta.to/u/t3dotgg/i-moved-off-of-next-js); [YouTube](https://www.youtube.com/watch?v=Sc5ca-VJdxY)). That is the steelman for Start as the tRPC-shaped full-stack host.

The institutional gap is real. tRPC has no `adapters/tanstack-start` export. Live tanstack.com example URLs for `with-trpc` **404’d** on 2026-09-21, APIs have churned (`createAPIFileRoute` versus file-route `server.handlers`), and T3 Chat moved tRPC **off Start file routes onto Nitro** after lazy API bundling failed at scale on Vercel ([Fetch adapter](https://trpc.io/docs/server/adapters/fetch); [Theo on X](https://tweets.vercel.fyi/x/theo/1997406196660400228)). Start is the better _design_ match and the weaker _docs and ops_ match. Next App Router is the opposite: first-class documented setup, streaming prefetch that TkDodo’s Advanced SSR guide already explains, and a dual-world that fights tRPC’s original model ([Advanced Server Rendering](https://tanstack.com/query/latest/docs/framework/react/guides/advanced-ssr/); [tRPC issue #6655](https://github.com/trpc/trpc/issues/6655)). Vite plus Fastify or Hono is cleaner still once the product _is_ an API: first-party Fastify (v5+) with WebSockets, community `@hono/trpc-server` on Workers, no RSC overlap, one router package, CORS or a same-origin proxy for cookies ([Fastify adapter](https://trpc.io/docs/server/adapters/fastify); [npm `@hono/trpc-server`](https://www.npmjs.com/package/@hono/trpc-server)). Theo’s own Vite+Hono Cloudflare rewrite worked, then lost to worker **JS size limits (3 MB free / 10 MB paid)** and the desire to deploy frontend and backend as one version ([Rosetta transcript](https://rosetta.to/u/t3dotgg/i-moved-off-of-next-js)). Split SPA+API is the best tRPC DX and the easiest way to reintroduce CORS, cookie SameSite bugs, and schema-skew. Reverse-proxy the API onto the web origin unless Expo already forces bearer tokens.

The ranking that follows from that tension is not a popularity contest. **Start wins “best suits tRPC.” Next App Router wins “best documented production default.” Fastify/Hono wins “the router is the product.”** Pages Router still has the most productized tRPC integration (`withTRPC`, SSR helpers) and should not be migrated for fashion. Remix and React Router 7 are a documented Fetch host with `createTRPCQueryUtils.ensureData` in loaders; they are not a reason to pick that framework _for_ tRPC ([Fetch adapter Remix snippet](https://trpc.io/docs/server/adapters/fetch); [createTRPCQueryUtils](https://github.com/trpc/trpc/blob/next/www/docs/client/react/createTRPCQueryUtils.md)).

## The 2026 companion stack has already left T3 --default behind

Language and runtime are not a shopping trip. **TypeScript `strict: true` is non-negotiable** for router inference and for Better Auth `$Infer.Session` across packages ([Quickstart](https://trpc.io/docs/quickstart); [T3 Introduction](https://create.t3.gg/en/introduction)). Production runtime is **Node LTS** (Next, Vercel, Cal.com). Bun is a documented install and local-test option, not the T3 workspace linker: a 2026 create-t3-turbo bun-migration PR still treated linker and duplicate-Vite bugs as a **blocker** ([TanStack React Query setup](https://trpc.io/docs/client/tanstack-react-query/setup); [create-t3-turbo PR #1457](https://github.com/t3-oss/create-t3-turbo/pull/1457)). Deno Deploy is a Fetch-adapter path, not a Next/T3 path ([Fetch adapter](https://trpc.io/docs/server/adapters/fetch)).

Validation is **Zod** unless a team already lives in Valibot or ArkType. tRPC’s own docs call Zod the default because the ecosystem (forms, `errorFormatter` `zodError` flattening, T3, Cal.com) assumes it; Valibot and ArkType pass through Standard Schema with no adapter ([Input and output validators](https://trpc.io/docs/server/validators); [Error formatting](https://trpc.io/docs/server/error-formatting)). Share one schema between `.input()` and the form library. Output validators stay optional; failed `.output()` becomes `INTERNAL_SERVER_ERROR`. SuperJSON is the T3/Cal.com transformer so `Date` values survive the wire; skip it in a lean stack that only returns JSON-safe primitives ([Data transformers](https://trpc.io/docs/server/data-transformers)).

Database pairing is **Drizzle plus serverless Postgres (Neon, or Supabase Postgres when the platform extras are wanted)**. T3 tells you to put `db` on tRPC context; table types flow into procedure returns without a generate step; Neon’s HTTP driver matches Vercel/edge single-query work, with the WebSocket/`postgres` driver reserved for interactive transactions ([T3 Drizzle](https://create.t3.gg/en/usage/drizzle); [Drizzle Neon](https://orm.drizzle.team/docs/connect-neon); [create-t3-turbo](https://github.com/t3-oss/create-t3-turbo)). Prisma remains the Cal.com-scale proof and a first-class T3 option; it is not the greenfield default. Kysely wins only when SQL _is_ the product. Do not run the Supabase JS client as a second CRUD API beside tRPC. PlanetScale MySQL and Turso/libSQL stay valid T3 `--dbProvider` choices, not the 2026 starting line.

Auth on a new tRPC app is **Better Auth**. Auth.js’s own migration guide now says the project is part of Better Auth and **new projects should start there**; create-t3-turbo already uses it; create-t3-app’s interactive CLI offers `--betterAuth` ([Migrating from Auth.js to Better Auth](https://authjs.dev/getting-started/migrate-to-better-auth); [create-t3-turbo](https://github.com/t3-oss/create-t3-turbo)). The tRPC pattern is identical across vendors: resolve the session **per request** in `createContext` from headers/cookies, expose it on `ctx`, throw `UNAUTHORIZED` from `protectedProcedure`. Clerk is the hosted alternative with an official `auth()` context guide ([Clerk + Next.js + tRPC](https://clerk.com/docs/guides/development/trpc)). Auth.js v5 is for existing NextAuth apps. **Lucia is deprecated** (March 2025); there is no successor library ([lucia-auth.com](https://lucia-auth.com/)). Browser sessions are **httpOnly cookies** plus `credentials: 'include'` on `httpBatchLink`. JWTs belong on Expo, third-party callers, and Better Auth’s JWT plugin, not in `localStorage`. Module-scope `createCaller(await createContext())` that calls Next `headers()` is a known production footgun ([tRPC discussion #5704](https://github.com/trpc/trpc/discussions/5704)).

UI stays **React**. That is where the Query integration, T3, Clerk’s guide, and Cal.com live. T3’s own axioms refuse to bundle a component kit; **create-t3-turbo** adds shadcn in `packages/ui` ([T3 Introduction](https://create.t3.gg/en/introduction); [create-t3-turbo](https://github.com/t3-oss/create-t3-turbo)). Forms default to **React Hook Form plus the same Zod schema as `.input()`**, which is what shadcn documents; TanStack Form v1 is the better pick when the app is already TanStack-shaped and fields are deeply nested ([shadcn React Hook Form](https://ui.shadcn.com/docs/forms/react-hook-form)). Realtime, when needed, is **tRPC SSE (`httpSubscriptionLink`) with `tracked()` reconnect**, not WebSockets; tRPC says SSE is easier and does not require a WS server. `wsLink` is for bidirectional streams on a long-lived Node process. PartyKit and Durable Objects are a separate room protocol beside tRPC, not a subscription transport ([Subscriptions](https://trpc.io/docs/server/subscriptions)).

Testing is **Vitest against `createCallerFactory`** for authz, Zod failures, and business rules, plus **Playwright** for cookie plus `httpBatchLink` plus UI, which is what the official Next+Prisma starter runs in CI ([server-side calls](https://github.com/trpc/trpc/blob/main/www/docs/server/server-side-calls.md); [next-prisma-starter](https://github.com/trpc/trpc/tree/main/examples/next-prisma-starter)). Hosting defaults to **Vercel plus Neon**. Cloudflare Workers is first-class for a thin Fetch/Hono router and a poor host for a large SSR React app. Fly/Railway/Docker Node is the path for Fastify WebSockets, Prisma without edge adapters, and Cal.com-like monoliths. Observability is `errorFormatter` plus adapter `onError` into Sentry, with PostHog around it: Cal.com’s pattern, not a tRPC APM product ([Error formatting](https://trpc.io/docs/server/error-formatting); [Cal.com architecture](https://calcom-cal-com.mintlify.app/developers/contributing/architecture)).

create-t3-app **7.40.0** still encodes a 2022-shaped `--default`: NextAuth v4, Prisma, Pages (`appRouter: false`), tRPC **pinned at 11.0.0**, classic `@trpc/react-query` plus `@trpc/next`, Zod 3 ([create-t3-app CLI package.json](https://raw.githubusercontent.com/t3-oss/create-t3-app/main/cli/package.json); [CLI source](https://raw.githubusercontent.com/t3-oss/create-t3-app/main/cli/src/cli/index.ts)). Interactive prompts now default App Router to yes and offer Drizzle and Better Auth, but the generated client has **not** switched to `@trpc/tanstack-react-query`. **create-t3-turbo is the batteries template that matches 2026 tRPC**: tRPC v11, Drizzle and Supabase, better-auth, Next 15 or TanStack Start v1 rc, Expo SDK 54, React 19, Tailwind v4, shadcn, pnpm ([create-t3-turbo README](https://raw.githubusercontent.com/t3-oss/create-t3-turbo/main/README.md)). T3 maintainers have already refused to replace tRPC with Server Actions: tRPC is “that data layer,” especially for React Query in client components ([create-t3-app#1456](https://github.com/t3-oss/create-t3-app/issues/1456)). TkDodo’s rule still stands: do **not** use Server Actions as a `queryFn`; use tRPC or an API route for client fetches, Actions for mutations that do not need the cache ([Advanced Server Rendering](https://tanstack.com/query/latest/docs/framework/react/guides/advanced-ssr/)). tRPC’s own Server Actions path is `experimental_` and “not a replacement for all tRPC mutations” ([Server Actions](https://trpc.io/docs/client/nextjs/server-actions)).

## Three hosts, one exported AppRouter, three product shapes

The invariant across variants is a **type-only `AppRouter` import**. Runtime server and database code must not ship in the web or React Native bundle. tRPC discussion #6980 and create-t3-turbo both treat `packages/api` as the extraction, with shared Zod that _runs_ on the client living in a types package ([trpc/trpc #6980](https://github.com/trpc/trpc/discussions/6980); [TanStack React Query setup](https://trpc.io/docs/client/tanstack-react-query/setup)). RSC `createCaller` is web-only. Expo always goes over HTTP, so procedures have to be designed as a public fetch contract from day one, with **bearer tokens** (SecureStore, Clerk `getToken`) rather than Next cookies ([DEV: Next + Expo tRPC v11](https://dev.to/hirodeath/sharing-trpc-v11-types-between-nextjs-and-expo-a-real-world-indie-web-ios-setup-3067); [Clerk + T3 Turbo](https://clerk.com/blog/clerk-t3-turbo)). A single Next or Start app can still be the HTTP server for mobile (one deploy, one version). The monorepo exists so a second runtime can import types without bundling `db`.

**Variant 1 is the primary: client-first interactive SaaS.** Dashboards, optimistic updates, subscriptions, typed client routing, little SEO. Host on **TanStack Start**, keep tRPC as the public API (Tanner’s line), put QueryClient in the router, prefetch in loaders with `ensureQueryData`. Expect to own the Fetch catch-all. At T3 Chat scale, be ready to lift API routes onto Nitro so Start’s lazy file routes do not become the outage. Swap RHF for TanStack Form if field trees are deep. This is the stack that _fits_ tRPC.

**Variant 2 is the production default: Vercel web product with RSC and a client island.** Marketing pages, SEO, one Next codebase, interactive app behind it. Scaffold from **create-t3-turbo**, keep `apps/nextjs`, put Drizzle on Neon, Better Auth on cookies, tRPC on `fetchRequestHandler`, and **upgrade the client to `@trpc/tanstack-react-query`**. Use RSC `createCaller` for data that never hydrates; prefetch plus `HydrationBoundary` for anything a client component will keep querying. Keep tRPC for mutations, cache, Expo, and SSE. Do not treat `create-t3-app -y` as current. Cal.com proves this shape at production scale (tRPC as the Next frontend’s primary API, Zod, SuperJSON, React Query) and also proves the serverless failure mode: a **single fat router on one Vercel function produced 15-second cold starts**, cut to about **2 seconds** by splitting handlers so Vercel emitted separate functions ([Cal.com cold starts](https://cal.com/blog/cal-com-cold-start-resolution-blog)). Lazy routers are a production concern, not a style preference.

**Variant 3 is API-heavy and multi-client.** Web SPA or Start UI, Expo, webhooks, maybe bidirectional streams. Extract `packages/api`, mount it on **Fastify v5** for Node and WebSockets or on **Hono** (`@hono/trpc-server` or raw Fetch) for Workers. Point Vite at the API through a **same-origin proxy** in development and a reverse proxy in production so cookies keep working for web; give Expo `Authorization`. Skip shadcn, superjson, SSE, and Playwright until the product needs them. Lean still means TypeScript strict, Zod on `.input()`, and `protectedProcedure`. Cloudflare is excellent for a small Hono router and a trap for a large SSR bundle. Railway/Fly is the WS and long-job host.

Theo’s 2026 talk refused a universal stack recommendation. The usable compression is: **Start when the router is Query-native UX, Next when the company is Vercel-and-RSC, Fastify/Hono when the router has more than one runtime.** Companion libraries stay put across all three.

## Drop tRPC when the consumer cannot import the router

tRPC is an internal TypeScript SDK. OpenAPI exists as first-party **`@trpc/openapi` alpha**: no annotations required, OpenAPI 3.1, subscriptions excluded, GET still encoded as tRPC `?input=`, transformers must match generated clients ([tRPC OpenAPI](https://trpc.io/docs/openapi)). That is a bridge, not a public API product. Community posts that still say “tRPC has no OpenAPI” are stale; treating alpha OpenAPI as equivalent to oRPC or ts-rest is an overstatement. Create T3 App’s external-API advice is still wrap a procedure in a normal HTTP handler or add OpenAPI metadata, because “the syntax can be cumbersome due to the RPC protocol” ([Create T3 App tRPC](https://create.t3.gg/en/usage/trpc)).

Public APIs, Swift/Kotlin/Java/C#/Python clients, partner Postman collections, and stable URL deprecation windows **flip the recommendation**. Sidlynx’s line is the right one: the mistake is not using tRPC internally; the mistake is pretending `AppRouter` is also the external contract ([When tRPC is not enough](https://sidlynx.me/blog/when-trpc-is-not-enough/)). Cal.com already dual-stacks: tRPC at `/api/trpc` with NextAuth cookies for the first-party web app, and a **separate Nest REST v2** with API keys, OAuth, and JWT for the Platform SDK and integrators ([Cal.com architecture](https://factory.ai/open-source-wikis/cal-com?page=overview%2Farchitecture.md)). React Native in the same TypeScript monorepo is still a tRPC-shaped product. Native iOS written in Swift is not.

oRPC is the closest “tRPC plus public contract” challenger: first-class OpenAPI 3.1, Standard Schema, TanStack Query **without** a React provider, Vue/Solid/Svelte/Angular Query marked first-party, and `toORPCRouter` for existing tRPC apps ([oRPC comparison](https://orpc.dev/docs/comparison); [Migrating from tRPC](https://orpc.dev/docs/migrations/from-trpc)). It is **not** replacing tRPC in T3. create-t3-app still asks “Would you like to use tRPC?” and oRPC’s own migrate snippets still pin `@orpc/*@beta`. Vendor benches on that comparison page (treat as vendor-provided) put oRPC HTTP RPC around **20k req/s vs tRPC 4.8k** on no-op handlers and a smaller gzip client once SuperJSON is in the tRPC figure. LogRocket’s split still holds: all-TypeScript one team → tRPC; OpenAPI/SDK/partners → oRPC ([LogRocket: tRPC vs oRPC](https://blog.logrocket.com/trpc-vs-orpc-type-safe-rpc/)). **ts-rest** is the contract-first REST answer (`It's just HTTP/REST`, optional OpenAPI) ([ts-rest](https://ts-rest.com)). **Hono RPC** (`hc<AppType>`) is typed `fetch` on a Hono server, not a procedure tree ([Hono RPC](https://hono.dev/docs/guides/rpc)). Eden Treaty is an Elysia/Bun feature. GraphQL via Pothos is the many-client field-selection product. None of these are “tRPC but better” for an internal React dashboard.

Framework-native stacks remove the _need_ for tRPC even when TypeScript is on both sides. tRPC’s RSC guide says so. Kent C. Dodds’s homepage quote is that Remix already gave him end-to-end typesafety, so he would not investigate tRPC ([tRPC homepage](https://trpc.io)). SvelteKit’s community adapter (`trpc-sveltekit`) advertised tRPC **v10** compatibility in the README that was fetched; kit `load` and form actions already type the server boundary ([trpc-sveltekit](https://github.com/icflorescu/trpc-sveltekit/)). Vue and Angular clients exist as community libraries. First-party `@trpc/*` clients in 2026 are vanilla, classic React Query, the new TanStack React Query package, and `@trpc/next` for Pages. Picking Svelte or Vue “because tRPC is better there” inverts the ecosystem.

License is MIT and not a constraint ([trpc/trpc](https://github.com/trpc/trpc/)). Strategic risk is **product overlap with RSC and Server Actions**, plus fat-router cold starts, plus OpenAPI remaining alpha. The library is adapting (RSC hydration guide, experimental Actions, React 19 proxy fix in PR #7336), not being abandoned. High-profile “we ripped out tRPC” posts are scarce; the real departures are architectural: never adopt it (Remix/SvelteKit), drop it for Actions on a one-client App Router app, or add REST beside it (Cal.com).

## Conclusion

The 2026 question is no longer “Next versus something else.” It is whether tRPC is the **public typed RPC into a Query cache** or a leftover data-access layer under RSC. If it is the former, Start (or Vite plus Fastify/Hono) is the honest host and Next App Router is a documented compromise you take for Vercel, SEO, and staffing. If it is the latter, skip tRPC. The practical bootstrap that does not lie to a new team is **create-t3-turbo**, Next as the first web app, `@trpc/tanstack-react-query` instead of the classic T3 client, Better Auth and Drizzle instead of NextAuth v4 and a Prisma generate step, and a `packages/api` boundary drawn before Expo shows up. Draw the REST/OpenAPI line the day a non-TypeScript consumer is on the roadmap, not the day they send a Postman collection. oRPC is the migration hatch if that day is year one; Cal.com’s dual stack is the hatch if tRPC is already the web app.
